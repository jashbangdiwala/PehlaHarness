Phase 1 You are here

Make it an agent

Today the bot can only talk. By the end of this phase it can act. It picks which of its tools to use, runs them and tells you what it did. You learn what an agent is by building one.

What you are building

Today. You send a message. The bot passes it to the model with one line of instructions and sends back whatever the model says. It has no memory of your previous message. Tell it what you ate and it may answer "Noted", but nothing is saved anywhere.

After Phase 1. You send one message:

You, in Telegram
had dal and rice for lunch, did 2h of AI study, how am I doing on my AI learning goal?

The EA saves the meal, saves the two hours, looks up your goal and replies with where you stand. One command then prints every step it took:

The one idea: a loop

Simon Willison's definition is the shortest accurate one: "An LLM agent runs tools in a loop to achieve a goal" (his post). Model, tools, loop. You already have the model. This phase adds the other two.

  1. The harness sends the model your message, along with a list of the tools it may ask for.
  2. The model replies in one of two ways: ordinary text, or a request to run a tool.
  3. If it asked for a tool, the harness runs the matching Python function and sends the result back to the model as another message. Go back to 2.
  4. When the model replies with text, the loop ends and you get the reply.

The model never runs anything. It only writes a request, and your code decides whether to carry it out. The whole of Phase 4 (security) rests on that fact.

Play one message through the loop

This is the exit-test message. Press Next and watch two things: which part of the loop is active, and what the model is sent.

What a tool call looks like

Three small pieces of JSON go back and forth. They are simplified here. You will see the real ones in step 3.

1 · The harness describes a tool to the model
{ "name": "log_food",
  "description": "Save something the user ate or drank.",
  "parameters": { "description": "string",
                  "meal": "breakfast | lunch | dinner | snack" } }
2 · The model asks for it
{ "role": "assistant", "content": null,
  "tool_calls": [ { "id": "call_1",
      "function": { "name": "log_food",
        "arguments": "{\"description\": \"dal and rice\", \"meal\": \"lunch\"}" } } ] }
3 · The harness runs it and reports back
{ "role": "tool", "tool_call_id": "call_1",
  "content": "Saved: lunch, dal and rice" }

The description in piece 1 is the only thing the model knows about your tool. Writing it well is prompt writing.

History

A model remembers nothing between calls. When a chat app seems to remember, the program around the model is sending the earlier messages again, every time. You are about to build that.

This is your first piece of context management: choosing what the model gets to see. More history means better answers and a bigger bill, because you pay for every token of history on every call. So you cap it.

3

Tool contract

Before the model can use tools, the harness needs one agreed definition of what a tool is. That definition is the contract. In your harness a tool is four things:

  1. a name, such as log_food
  2. a description in plain English, saying what it does and when to use it
  3. a schema: the arguments it takes and their types
  4. a Python function that does the work

The first three are sent to the model, which reads them like documentation. The fourth never leaves your Mac.

This step also changes the gateway. Until now it returned a string. From now on the model can answer in two ways, text or a request for tools, so the gateway returns the whole message. There is still no loop. You make one live call and look at what a tool request really is.

4

Loop

This is the piece that makes it an agent, and the file from this phase you should know best. It is short.

  1. Call the model with the messages and the tool list.
  2. If it answered in text, return the text. Finished.
  3. If it asked for tools, run each one, add the results to the messages and go back to 1.
  4. If this has gone round six times, stop anyway.

Three rules keep the loop safe:

  • A step cap. A confused model can ask for tools forever. Every round costs money. Six is plenty for the EA.
  • Errors go back to the model as text. If a tool crashes, the model is told what went wrong and can try again or tell you. One bad tool call should not take the bot down.
  • Every step is logged. You cannot pause a model and step through it the way you debug code. The log is how you find out what happened.

Give Claude Code this

Prompt
Do Phase 1 step 4: the agent loop.

core/loop.py, one function: run(messages, tools, parent_id, max_steps) -> str
- Call the gateway with the messages and tools.
- If the reply has no tool_calls, return its text.
- Otherwise append the assistant message, run every requested tool, append one role "tool" message per call (with its tool_call_id), and call the gateway again.
- If a tool raises, the tool name does not exist, or the arguments are not valid JSON: do not crash. Send the error back to the model as that tool's result so it can recover.
- After max_steps model calls without a text answer, stop and return a short "I couldn't finish that" message.
- Log each tool run as a tool_call event (name, arguments, result or error, seconds). Its parent is the model_call event that asked for it, so the gateway needs to hand back the id of the model_call event it logs.
- Put MAX_STEPS = 6 in config.py.

agents/ea/agent.py: respond() now calls loop.run(), with an empty tool list for now.
channels/telegram.py: split a reply longer than 4096 characters into several messages. That is Telegram's limit.

Tests, all against a stubbed gateway with no network:
- a text answer on the first call is returned
- one tool call, then text: the tool ran once and its result was in the second request
- two tool calls in one reply: both run, and two tool messages are sent back
- a tool that raises: the error text reaches the model and the loop continues
- an unknown tool name: the same
- a model that never stops asking: the loop ends after max_steps

Done means: pytest passes and the bot still chats normally.

5

EA tools

The loop works. Now the EA gets something to do with it. Four small tools, each a plain Python function that reads or writes a table:

ToolDoesTable
log_foodSaves something you ate, and which meal it was.ea_food
log_timeSaves minutes spent on a category.ea_time
set_goalSets a weekly target in minutes for a category.ea_goals
review_goalsCompares each goal with the time logged in the last 7 days.reads both

Three habits of good tool design show up here, and you will reuse them for every tool you ever write:

  • One tool, one job. Small models choose better between four clear tools than inside one tool with many modes.
  • The description is a prompt. Say what the tool does and when to use it.
  • Return a short sentence. The result goes back to the model, so write it for a reader: "Saved: lunch, dal and rice".

A trap you would otherwise hit: you set a goal for "AI learning", the model logs time under "ai study", and the review says you have done nothing. The names have to match. The prompt below handles it in two ways. Category names get a fixed format, and the EA is told the existing categories on every turn.

6

Policy

The model chooses which tool to call. But the model's output is text you did not write. It can be wrong, and later it can be steered by text the model has read, which is called prompt injection. So the harness keeps the final say: one function, called before every tool run, answers "is this agent allowed to use this tool?"

The list of what each agent may use is kept in config.py, apart from the agent's own code. Adding a tool then takes two deliberate acts: writing it, and granting it. A bank would call that list entitlements.

Today the check is small and refuses nothing the EA needs. Its value is that the place for it now exists. In Phase 4 you add rules such as "this tool needs my approval first" in that one place, without touching the loop.

Give Claude Code this

Prompt

core/loop.py: run() takes the agent name and calls policy.allowed() before every tool run. This is the only place in the codebase where a tool function is called. A refused call does not run. The model gets "Tool not permitted" as the tool result, and a policy_refused event is logged with the agent, the tool name and the arguments.

7

Trace

A trace is the full record of one run: every model call and every tool call, in order, with what went in and what came out. Since v0 every event has carried a parent_id, so the tree already exists in your database. This step adds a command that prints it.

You will use it every day from here on. When the EA does something odd, the trace shows you which step went wrong. In Phase 2 your evals read these same traces.

Give Claude Code this

Prompt
Do Phase 1 step 7: the trace command.

python -m core.events recent              the last 10 messages with their ids
python -m core.events trace <message_id>  one message's tree
python -m core.events trace last          the most recent message

The tree is indented by parent and shows: the message; each model call (seconds, input tokens, output tokens, how many tools it asked for); each tool call (name, arguments, result or error); any policy refusals; the reply. 1. Run the exit test three times

Make sure a goal exists (you set one in step 5). Then send the exit test message from the top of this page three times, a few minutes apart, and run python -m core.events trace last after each.

A pass means log_food, log_time and review_goals each ran, and the reply says where you stand on the goal. Three times because models do not behave identically every run. One pass can be luck. That thought is the start of Phase 2.

2. Save one trace

Copy one trace into docs/phase-1/trace.txt. Read it first. It is going on GitHub, so it must contain nothing you would not publish.

3. Write the one-pager

docs/phase-1/README.md, one page, four headings:

  • What I built. A few sentences and the loop drawn in text.
  • What broke. The real problems you hit, and what fixed each one.
  • What I measured. From your traces: model calls per message, tokens per message, seconds per message, and how many of the three exit runs passed.
  • What changes at bank scale. Who approves a new tool? Where does the log live and who may read it? What happens when the model provider is down?

4. Write the decision record

An ADR (architecture decision record) is half a page that explains one design decision to someone who was not there. Write docs/adr/001-core-and-agents.md with three headings:

  • Context. One agent today, more coming. You want one place to measure cost and one place to enforce security.
  • Decision. Shared machinery in core/, one folder per agent, core/ never imports an agent, every model call goes through the gateway, every tool run goes through policy.
  • Consequences. What this makes easier, and what it makes harder.

Do alongside

Two small habits during this phase make Phase 2 possible. Keep both in private/notes.md, which git ignores, because they contain your real messages.

  1. Save 20 real messages. Each time you send the EA something real, paste it into the file with one line saying what should have happened. In Phase 2 these become your test set.
  2. Note every bad reply. One line each: what you asked and what went wrong. In Phase 2 this list tells you what to measure.

You have got it when

You can answer these out loud, without notes. They are the questions an interviewer asks about agents.

  • Draw the loop from memory, including both ways it stops.
  • What is the difference between a workflow and an agent? Which is your EA, and why?
  • What goes into the model's context on every call? What gets left out?
  • What happens when a tool fails, and why does the error go back to the model?
  • Why does code check the model's tool request before running it?

Check yourself

Six questions. Each answer explains itself and links back to the step that covers it.

1. The model asks for log_food. What runs the function?

Your harness runs it, on your Mac. The model only writes a request. Your loop looks up the function and calls it. Back to Step 3

2. You asked "what's my name?" and the bot got it right. Where was your name kept?

In the events table, and sent again with the new message. A model keeps nothing between calls. The harness read the earlier turn from the log and sent it again. Back to Step 2

3. A tool raises an exception halfway through a run. What should the loop do?

Send the error text back to the model as the tool result. The model can then retry with better arguments or tell you what went wrong. Back to Step 4

4. Why is the model's own tool request added to the messages before the result?

Because the model has no memory: the next call must show what it asked for. Each call starts from nothing. Without the request, the result would be an answer to a question the model cannot see. Back to Step 4

5. The model asks for a tool that exists but is missing from TOOL_ALLOWLIST. What happens?

It is refused, the model is told, and a policy_refused row is written. Writing a tool and granting it are two separate acts. Only the allowlist grants. Back to Step 6

6. Which of these is the model not sent on a call?

A meal you logged three weeks ago. Old rows stay in the tables. The model only learns about them if a tool reads them during the run. Back to Step 5
