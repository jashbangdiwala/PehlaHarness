Harness Handbook

The guide to PehlaHarness. Read this page first, and read it again whenever you come back after a break. It says what you are building, where you are, and what to open next.

What you are building

A language model does one thing. Text goes in, text comes out. It cannot remember yesterday, save anything, look anything up or check its own work.

A harness is the program around the model that does all of that. It decides what text goes in, runs the actions the model asks for, keeps a memory, guards your secrets, records every step and measures whether the answers are any good. The model is the engine. The harness is the rest of the car.

Colour means the same thing in every diagram in this handbook:

  • the model
  • your harness code
  • tools
  • stored data
  • risk or refusal
  • someone else's computer

You are building one from scratch in Python, one small piece at a time. Its first job is to run your EA (executive assistant): a Telegram bot on your Mac that logs your food and your time and tells you how you are doing against your goals. You will use it every day, so you will have real data to test with.

Frameworks such as LangChain hide these pieces. Building each one once, small, is the fastest way to learn what it does and why it is hard. The pieces are also the things companies struggle with when they put AI into production: quality, cost, security and audit.

Why you are building it

One piece of work, two results.

  1. You learn the subject properly. Each phase covers one area an AI subject-matter expert is expected to know cold: agents, evals, cost, security, memory, multi-agent systems, governance.
  2. You get a portfolio. Each phase ends with four things you can show someone: a working demo, numbers from your own system, a one-page write-up and a short record of the main design decision.
ShowA demoIt working, on video or in a screenshot.
ProveNumbersMeasured on your own system.
ExplainA one-pagerBuilt, broke, measured, at bank scale.
DecideAn ADRThe main design choice, in half a page.

The aim is to be able to say things like: "My red-team agent got my assistant to leak my goal list. Here is the trace, and here is the fix."

The whole system in one picture

One rule holds the design together: core/ knows nothing about any particular agent. That rule is what lets you add a second agent later without touching the first.

Today the code is three flat files (main.py, egress.py, events.py). Phase 1 moves them into this shape. How it works follows one message through what runs today.

Where you are

Each phase answers one question. The order is fixed by what depends on what, and there are no dates. Pass a phase's exit test, then move on.

  1. 0BotDone A Telegram bot that only answers you, reaches the model through one guarded door and logs every step.
  2. 1Agent loopYou are here How does an agent work? The model gets tools and a loop. The EA can log food and time and review goals.
  3. 2EvalsLater How do you know it is good, and that a change did not break it?
  4. 3CostLater Where do the tokens and the money go, and how do you cut them without losing quality?
  5. 4SecurityLater How do you stop the agent being tricked, and limit the damage when it is?
  6. 5MemoryLater How does it remember more than the last few messages?
  7. 6Game agentLater Does the harness hold up for a completely different agent? A second agent plays a browser game.
  8. 7Multi-agentLater When do several agents beat one, and what does it cost?
  9. 8Enterprise packLater What would a bank need to see before it approved this?

Two side tracks run next to the phases: Models (fine-tune small open models and publish them) and Lab (build a tiny language model from scratch). The Roadmap has the detail for everything after Phase 1.

How to work through a phase

  1. Read one thing first. Each phase names one article or talk. Read it before you build, so the words in the guide already mean something.
  2. Build one step at a time. Each step has a prompt to give Claude Code. One step, one session, one commit.
  3. Review the diff. Claude Code writes the code, so the review is where you learn. Each step lists which file to open and what you should be able to answer before you accept it.
  4. Pass the exit test. Each phase has one concrete test.
  5. Write it up yourself. One page in your own words and a short decision record. This is the portfolio piece, so it has to be yours.

Rules that never change

  • Every model call goes through the gateway. Nothing else talks to a model.
  • Secrets live in the macOS Keychain. They are never printed, logged or committed.
  • ea.db and allowed_id.txt never go to GitHub. They hold your messages and your Telegram ID.
  • Models are open-weight and US-origin. Model spend stays under $20 a month.
  • Raw EA logs are never published. Anything public is synthetic or scrubbed, and you read it before it goes up.

Words you need

Twelve terms carry most of this handbook. Each one gets a fuller explanation in the phase where you build it.

Model
The language model (LLM). Text in, text out.
Token
The unit a model reads and writes, roughly three-quarters of an English word. You pay per token, in and out.
Context
Everything sent to the model in one call: instructions, earlier messages, tool descriptions and the new message. The model knows nothing else.
System prompt
The standing instructions at the top of the context.
Tool
A function the model can ask the harness to run, such as log_food. The model asks. Your code runs it.
Agent
A model that uses tools in a loop until the job is done.
Harness
Everything around the model that makes the agent work.
Gateway
The one function allowed to call a model. Redaction, logging and spending limits live there.
Policy
The check that decides whether a tool is allowed to run.
Trace
The step-by-step record of one run: every model call and tool call, in order.
Eval
A repeatable test of the agent's behaviour, the way a unit test checks code.
ADR
Architecture decision record. Half a page: the situation, the decision and what follows from it.
